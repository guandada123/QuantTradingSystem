- **✅已升级(2026-09-06)**: 是
- **相关条目**: `2026-09-02-freshness-measures-uptime-not-data.md`（同族：新鲜度检查量错对象。

## 现象

回测正常出报、无报错、耗时正常（13s）、PG 落库成功、Top5 完整 —— 全链路绿灯。
但 `daily_quote` 的行数分布是这样的：

```
2026-09-04   (无数据)
2026-09-03       44   <-- 残缺
2026-09-02       44   <-- 残缺
2026-09-01     4893   <-- 最后一个完整交易日
2026-08-31     4623
2026-08-28     4693
```

**连续 3 个交易日灌库中断**，而 `report_date=2026-09-04` 的回测实际跑在截止 **09-01** 的数据上。

更隐蔽的是：那 44 只标的是 `000001.SZ … 000068.SZ` —— **按代码升序的前 44 只**。
两天完全一致，说明灌库任务每天死在同一个位置，是确定性中断，不是抖动。

## 根因链

```
灌库任务中断（只写了 44/4893 只，按代码升序）
   ↓
MAX(trade_date) 仍返回 "2026-09-03"（截断日也算"最新"）
   ↓
三处新鲜度/完整度检查全部判"数据可用"：
   ├─ data_fetcher.py:101   SELECT MAX(trade_date) → "可用(本地优先)"  ← 被骗
   ├─ data_quality.py:179   _probe_latest 同样是取最新一条             ← 被骗
   └─ report_service.py:116 HAVING COUNT(*) >= 1000                    ← 唯一没被骗的
   ↓
report_service 的基准日正确回退到 09-01，但 K 线数据本身还是 09-01 的
   ↓
出报成功，report_date 写 09-04，无任何告警 → 静默错误
```

关键点：**09-03 那次修复只补了 report_service 一处的 `HAVING COUNT(*) >= 1000`，
没有把这个口径推广到另外两处，也没有修灌库任务本身。** 所以"修过一次"反而
制造了虚假安全感 —— 日志里能看到「流动性筛选基准日 = 2026-09-01（跳过未灌完的交易日）」，
看起来像"已经处理过了"，实际 K 线数据照样是陈的。

## 根因（追到第二层才见底）

第一层表象是「灌库任务中断」，但**为什么中断**才是关键。查 `automation.log` 拿到执行历史
（UTC，+8 = 北京时间）：

```
09-01T08:30Z start → 08:39Z finish   success=true   9.8min   → 09-01 完整 4893 行 ✅
09-02T08:30Z start → 13:53Z CANCELLED timed out     5h23m    → 只写进 44 行
09-03T08:30Z start → 16:11Z CANCELLED timed out     7h41m    → 只写进 44 行
09-04T08:30Z start → 无 finish（本次排查时仍在飞）
```

**真因是任务被超时杀掉，不是数据源故障。** 而它为什么慢到必被杀：

```python
ap.add_argument("--days", type=int, default=120, ...)   # 120 日 ≈ 80 个交易日
# × 5044 只 ≈ 40 万行，且 upsert_rows() 每只股票新建一次连接 + 逐行 cur.execute
# → 实测 8~12min
```

自动化调度器在超发环境里给它的实际执行窗口远小于此 → 每只股票各自 commit，
杀掉时已完成的部分**已经落库且无从回滚** → 每次都恰好剩下排序最前的 44 只。

**44 这个数字的来源**：`load_pool()` 按 `ts_code` 升序提交给 32 并发线程池，
前 44 个 future 在被杀前完成并各自 commit，其余全部丢弃。
两天完全一致 —— 这正是"确定性中断"的指纹（见下）。

顺带排除的假设：腾讯 WAF 频控。**实测两个 host 在低并发下 10/10 全部成功**，
`web.ifzq.gtimg.cn` 与 `ifzq.gtimg.cn` 均正常；32 并发跑满 5044 只也只需 30s。
频控不是本次原因（但确实是 09-03 那次事故的原因，别混淆两次）。

## 修复（三层）

**第 1 层 · 补数据**：手动增量补跑，覆盖缺口即可，不必重跑 120 日
```bash
$PY .workbuddy/scripts/qts_daily_backfill.py --days 5     # 34s，23186 行
```
结果：09-02 44→**4573**、09-03 44→**4574**、09-04 0→**4892**。（09-01 4893 本就完整）

**第 2 层 · 结果层标注**（brief 自带数据出处，让静默错误无法发生）
1. `report_service.py` 新增 `_probe_data_freshness()`：
   用「行数 >= 1000」判定完整交易日，返回
   `{data_as_of, data_stale, incomplete_sessions}`，1 小时进程内缓存。
2. `generate_daily_brief()` 把这三个字段注入 `summary`，滞后时打 WARNING：
   ```
   [Brief] ⚠️ 数据滞后: 回测数据截至 2026-09-01, report_date=2026-09-04;
           不完整交易日=['2026-09-02', '2026-09-03']
   ```

**第 3 层 · 写入方自检 + 根因参数修正**
1. `qts_daily_backfill.py` 默认 `--days 120 → 10`（≈7 个交易日，35~50s）：
   每日维护只需补最近缺口，且自带"前几日失败、今天跑一次就能补回"的自愈窗口。
   历史深度另跑 `--days 120`，不挂每日任务。
2. 新增 `verify_coverage()` + `--min-coverage 0.9`：跑完按「最新交易日的行数」自检，
   不足则 `sys.exit(1)`。实测双向有效（97% @0.9 放行 / 97% @0.99 拦截；事故值 0.87% 必被拦）。
3. 修正 automation-1784811393302 的校验步骤：原校验
   `MAX(trade_date)` + `COUNT(DISTINCT ts_code) WHERE trade_date >= 两月前`
   **两项都看不出截断**，已换成「只查最新交易日一个日期的行数 >= 4000」。
4. **`data_fetcher.py` 的 `_local_db_fresh()` 同样改为行数门槛口径**（此前是漏网的那 1/2）：
   同时取 `MAX(trade_date)` 与「行数 ≥1000 的最后一个交易日」，用后者判新鲜；
   两者不一致即识别为**截断态**。
   ⚠️ 关键取舍：截断态**仍返回 True 留在本地库，不退回网络** ——
   本函数一返回 False，上层会对池中每只股票逐个发网络请求，
   1232 只立刻触发腾讯 WAF 频控，就是 09-03 那次 14min+ 雪崩的同一条路径。
   残缺的本地数据仍优于打爆网络，但必须打 WARNING 暴露出来。
5. 6 条回归测试 `tests/test_data_fetcher.py::TestLocalDbFreshnessTruncation`，
   其中 `test_truncated_day_still_uses_local_but_warns` 专门锁死上述取舍
   （断言 `ok is True` 且 warning 恰好一次），防止后人"顺手改成走网络"重新引入雪崩。
6. **`data_quality.py` 加完整度维度**（`_probe_completeness()`）。
   `DataQualityRule` 新增 `db_group_col` / `min_rows_per_day`，按分区查最新一期的行数；
   `check_freshness()` 改为**先判完整再判新鲜**，不完整直接判不通过。
   10 条回归测试 `tests/test_data_quality.py::TestProbeCompleteness`
   + `TestFreshnessRespectsCompleteness`，含 SQL 注入标识符白名单守卫。

**根因层 · 消除超时本身**：`upsert_rows()` 由逐行 `cur.execute` 改为
`psycopg2.extras.execute_values` 批量提交（`page_size=1000`）。
`--days 120`（393,751 行）实测 **8~12min → 41s，约 15×**。
原先"每只股票新建一次连接 + 逐行 INSERT"是主要瓶颈，不是网络下载。

全量测试套件 **1308 passed / 3 skipped**（基线 1302，+6 条新测试），无回归。

## 教训

1. **`MAX(date)` 不是新鲜度，完整度才是。** 任何"数据是否够新"的判断，
   都必须配一个行数/覆盖率门槛。只查 `MAX` 的检查在面对截断写入时 100% 失效，
   而且失效方向永远是"误报为健康"。
2. **修一处不算修完一类。** 同一份数据被三个模块各自判新鲜度时，
   改了一个就等于埋雷：日志里出现"已跳过未灌完的交易日"会让人以为问题已解决。
   **改完必须全局 grep 同类模式**（这次是 `MAX(trade_date)`，命中 2 处漏网）。
3. **结果层要自带出处标注。** 一份报"2026-09-04 结论"的产物，必须携带
   "数据截至 X"。否则下游所有引用（晚报、飞书卡片、选股建议）都是无源之水。
4. **判灌库是否健康，看行数分布不要看最新日期。** 一行 SQL 就能定生死：
   ```sql
   SELECT trade_date, COUNT(*) FROM daily_quote
   GROUP BY trade_date ORDER BY trade_date DESC LIMIT 10;
   ```
   正常交易日 ~4700-4900 行，本次 44 行。
5. **确定性中断有指纹**：连续多天截断在**完全相同的标的集合**（按升序的前 N 只）
   → 是任务死在同一处（数据/异常/配额），不是网络抖动。抖动的话每天截断位置会变。
   本次两天都是前 44 只，据此直接排除网络因素，转向查执行历史。
6. **"任务超时被杀"和"数据源故障"表现一样，但处置完全不同。**
   区分方法是看 `automation.log` 的事件对（`run start` / `run finished` / `CANCELLED`），
   而不是看产物。产物只会告诉你"写了多少"，不会告诉你"为什么停"。
7. **默认值即风险。** 一个"跑得动但跑不完"的默认参数（`--days 120`，8~12min）
   挂在有时限的调度上，等价于埋了一颗按天引爆的雷。
   常驻任务的耗时预算必须显著小于调度窗口，而不是"理论上能跑完"。
8. **自检要放在写数据的那一方。** 调用方做校验时，它只能看到"数据库里现在有什么"，
   无从判断"本来应该有多少"；写入方才知道标的全集是多少。
   本次调用方的校验连续 3 天全绿就是证据。

9. **新鲜度 ≠ 完整度，两者正交，必须各查一次。** 详见下方更正段落里的三变体表。
   新建健康度检查时的验收问题：**「数据只写进去 1% 时，这个指标会变吗？」**
   会变才有效。三个变体的失效方向无一例外都是"误报为健康"。

## ⚠️ 更正：我先前对 `data_quality.py` 的判断是错的

排查中途我曾在本文档写下「`data_quality.py:179` `_probe_latest()` 仍是 MAX 口径，
需推广 `HAVING COUNT(*) >= N`」。**这个说法错了**，实际查库确认：

```python
DataQualityRule("每日行情", "daily_quote",
    db_table="daily_quote", db_ts_col="updated_at")   # ← 是 updated_at，不是 trade_date
```

它 MAX 的是**写入时间戳**，所以根本不存在"MAX(trade_date) 指向残缺日"这个问题。
它看不见截断是出于**另一个原因，而且更值得记**：

> **新鲜度回答「最后一次写入是何时」，完整度回答「那次写入写全了吗」—— 两者正交。**
> 灌库只写进 44/5044 只时，`updated_at` 照样是"刚刚"，于是新鲜度检查**完全免疫**，
> 连续 3 天判为新鲜，而当天的完整度只有 0.9%。

所以正确的修补不是把 `HAVING COUNT(*) >= N` 套上去（那会把语义搞混），
而是**新增一个独立的完整度维度**，并让 `check_freshness()` 先判完整再判新鲜。

这已经是同一族问题的第三个变体了，值得单独记一笔：

| 条目 | 检查量到的是什么 | 本应量什么 |
|---|---|---|
| 09-02 `freshness-measures-uptime-not-data` | 容器 uptime | 数据最后更新时间 |
| 09-04 `data_fetcher` | `MAX(trade_date)` | 行数达标的最后一个交易日 |
| 09-04 `data_quality` | `MAX(updated_at)`（写入时刻） | 那次写入的覆盖率 |

**共同模式：每一次"新鲜度"都量到了一个真实但无关的量，且失效方向永远是"误报为健康"。**
新增任何健康度检查时，先自问：这个指标在数据只写进去 1% 的时候，会变吗？会变才是有效的。
