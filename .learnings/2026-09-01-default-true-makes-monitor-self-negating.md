- **日期**: 2026-09-01

- **状态**: 已修复并部署（QTS commit `63f63a3d`，未 push）
- **✅已升级(2026-09-06)**: 7 条

## 现象

`quant-strategy` 每 5 分钟打一行数据质量日志（`run_loop(interval=300)`）：

```
数据质量检查完成 | 评分: 55/100 | 交易日: True | 通过: 7/7
```

**同一行里两个数字互相打架**：评分只有 55 分（扣了 45），却说 7 项全通过。

24h 量化：**295 次检查里 251 次（85%）处于这个状态**，仅 42 次是 100 分。
也就是说，这个"用来发现数据问题"的监控，**绝大多数时间都在报告"一切正常"**。

## 根因

```python
# ① freshness 检查项的 dict 里，压根没有 passed 这个键
results["checks"].append({
    "type": "freshness",
    "source": rule.source,
    "fresh": is_fresh,
    "delay_seconds": delay,
    "max_allowed_minutes": rule.max_freshness_minutes,
})          # ← 没有 passed

# ② 统计时用了「键缺失即默认通过」
sum(1 for c in results["checks"] if c.get('passed', True))
#                                                    ^^^^ 毒点
```

7 项检查 = 2 项 `source_online`（**有** `passed`）+ 5 项 `freshness`（**没有**）。
于是 5 项 freshness 无论多陈旧都被算作通过，只剩 2 项在真实计分。

评分 55 = 100 − 3×15，即 3 条 freshness 规则超时 1 小时以上；
而"通过数"恒等于 7。**监控的严重度（分数）和结论（通过数）来自两套互不相干的口径。**

## 为什么没人发现

- 不报错、不告警、健康检查全绿 —— 唯一出口就是那一行日志。
- 两个数字**在同一行紧挨着打印**，但读日志的人只看「通过 7/7」就滑过去了。
- `run_check()` **此前没有任何单元测试**（`tests/test_data_quality.py` 只覆盖
  `check_freshness` / `check_gaps` 等原子方法），集成路径零覆盖。

## 修复

1. `freshness` 检查项补 `passed`，语义固定为 **「是否触发扣分」**：
   `passed = not (not is_fresh and delay > 3600)`
   → 保证 `评分 = 100 ⟺ 通过 N/N`，两个口径不再各说各话。
2. 统计改为 `c.get("passed") is True` —— **键缺失算不通过**（fail-safe）。
   一个报不出状态的检查项，没资格被默认为通过。
3. 日志追加失败明细：`| 不通过: freshness:realtime_quote, freshness:index_quote`。
4. 新增 5 条回归用例，锁死"扣分 ⇔ 不通过"的一一对应关系。

## ✅已升级(2026-09-06)（7 条）

1. **`.get(key, True)` 是监控代码里的头号毒写法。** 默认值取 True 等于宣布
   "不知道就算好"。凡是统计"通过/健康/成功"的地方，默认值必须是 **False**。
2. **同一行输出里的两个数字必须能互相印证。** `评分 55` 和 `通过 7/7` 挨着打印，
   自相矛盾却存活数月 —— 因为没人同时检查两个数字。**能自相矛盾的指标要断言其一致性。**
3. **扣分规则与通过规则必须是同一个布尔。** 两套阈值（扣分要 >1h、通过看 SLA）
   必然产生"既不算通过也不扣分"的死区。把 `passed` 定义成"是否触发扣分"即可消除。
4. **集成路径（`run_check`）没有测试，原子方法有测试，是典型的覆盖倒挂。**
   越是"汇总/报告"型函数越要测 —— 它错一次，下游所有消费它的判断全错。
5. **「有输出」不等于「输出可信」。** 这个监控 295 次/天兢兢业业地打印，
   85% 的打印内容是错误的。频率高、格式规范、不报错，反而让它更可信也更危险。
6. **给汇总结果加"失败明细"是零成本高收益。** 只报 N/N 时值是死的；
   报出不通过项的名字，读者一眼就能判断是不是真问题。
7. **验证改动的"正确口径"要挑能暴露差异的场景。** 重启后首拍是 100/100（种子时间戳刷新鲜），
   看不出修复效果；必须**人为构造陈旧状态**才能证明新代码路径生效。

## 坑（实犯）

1. **`docker exec` 不带 `-i` 时 stdin 不转发**，heredoc 脚本静默无输出、exit 0 ——
   极易误判成"脚本跑通了但没打印"。容器里跑内联 Python 必须 `docker exec -i -w /app`。
2. **`grep -rn --include=*.py` 在 zsh 下会被当 glob 展开**，无匹配时报
   `no matches found` 并**整条命令失败**（连后面的指令都不执行）。
   跨目录搜代码用 Grep 工具，别在 zsh 里裸写 `--include`。
3. 容器日志时间戳是 **UTC**（`Z` 后缀），分桶统计后必须 +8 才能与 cron 配置（CST）对齐。
