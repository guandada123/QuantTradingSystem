# Provider 吞掉限频异常 → 批量任务对超限源发起 4494 次无效调用

- **日期**：2026-09-01（统一巡检中枢 run#57 发现并修复）
- **级别**：P1（工程缺陷，非策略参数）
- **状态**：已修复并部署验证

## 现象

`quant-strategy` 近 24h 日志中 **4878 条 Tushare 频率超限**：

| 接口 | 条数 | 限频阈值 | 时间分布 |
|---|---|---|---|
| `daily` | 4494 | 50 次/分钟 | **4518 条集中在 07 时(UTC)=北京 15:00-16:00** |
| `index_daily` | 384 | 5 次/天 | 均匀分布（每 30min × 8 指数） |

`daily` 的 4494 条对应「日行情刷新」cron（`hour=15, minute=10` CST），
遍历 4494 只标的、耗时 643.8s，**Tushare 路径 100% 失败**，数据全靠降级源兜底
（当日 `daily_quote` 有 4573 行 → 表象正常）。

## 根因（三处叠加）

1. **Provider 吞异常**：`shared/quote_provider/tushare.py:153` 的 `except` 一律
   `logger.error(...)` 后 `return []`。限频错误与「无数据」**同构**，降级链无法区分。
2. **降级链无熔断**：`DataService._call_provider_with_fallback()` 只看
   `validator(result)`（`len(r) > 0`）。收到 `[]` 就换下一个源，但**不记得上一个源刚超限**，
   下一只标的又从 Tushare 重新开始 → 4494 次撞墙。
3. **失败路径不限流**：`sync_daily_data()` 里 `self._sleep_rate_limit()`（0.3s）
   只在**成功**分支执行；`failed += 1; continue` 在 sleep 之前 → 连续失败时全速喷射。
   且 0.3s = 200 次/分，本就高于 Tushare 的 50 次/分。

## 修复（3 文件，bind mount 即时生效）

- `shared/quote_provider/base.py`：新增 `RateLimitError` + `is_rate_limit_error()`
  + `RATE_LIMIT_MARKERS`（单一真源，避免各 provider 各写一份）。
- `shared/quote_provider/tushare.py`：`get_daily_kline` / `get_index_realtime`
  命中限频时**上抛** `RateLimitError`，不再伪装成空结果。
- `strategy-service/services/data_service.py`：降级链增加**数据源级冷却**
  （`_source_cooldown`，默认 300s）；冷却期内跳过该源，首次命中打点告警。

## 验证（三层）

| 层 | 方法 | 结果 |
|---|---|---|
| 注入故障 | 假 provider 恒抛 `RateLimitError`，跑 50 次 | Tushare 只被撞 **1 次**（修复前 50） |
| 真实 API | 同一标的连打 80 次 | 第 48 次触发限频 → 熔断 → **实际只打 48 次**，剩余 32 次 COOLDOWN 跳过 |
| 回归 | `pytest tests/test_quote_provider.py` + `test_data_service.py` | **33 + 57 = 90 passed**；ruff check 通过 |

**收益推演**：日行情刷新对 Tushare 的无效调用 4494 → 约 50（**-98.9%**），
任务耗时预计从 643.8s 显著下降，且消除被 Tushare 升级处罚的风险。

## 待办（未做，避免过度改动）

- `sync_daily_data` 失败路径仍未 sleep（第 3 点只修了熔断，未动节流）。
  加了会让 4494 只多耗 22min，收益不明，**留待观察**。
- `_sleep_rate_limit` 0.3s 与 Tushare 50次/分 不匹配，但熔断已覆盖主风险面。
- 该修复为**冷却期内完全跳过**；若需更精细可改成令牌桶，当前无必要。

## ★ 升级候选（×5）

1. **「吞异常返回空」是监控与降级的头号杀手** —— 错误一旦被降级成"空结果"，
   上层所有基于异常的判断（熔断、告警、重试）全部失效。
   **错误语义必须在跨层传递中保持可区分**：系统性错误（限频/鉴权/配额）
   必须上抛或打标，只有"确实没有数据"才返回空。
2. **降级链必须有记忆** —— 只能"试下一个源"而不能"记住上一个源刚失败"，
   在批量场景（N 只标的 × M 个源）下会把单点故障放大 N 倍。
   降级 ≠ 遗忘，短时熔断是降级的必要组成。
3. **"部分成功掩盖完全失败"第三次复现** —— 前两次：QTS `backtest_reports` 落库失败但仍推飞书、
   pmf 3 个作业静默死亡。本次：Tushare 路径 100% 失败但日线数据照常有（靠降级源）。
   **校验数据管道必须逐源校验，不能只校验最终产出**。
4. **失败路径往往是限流的盲区** —— 节流代码写在成功分支是常见笔误，
   而系统最需要节流的时刻恰恰是**批量失败**时。
   加限流时要问：**失败/异常/超时路径走不走这条 sleep？**
5. **时间分布是定位元凶最快的切片** —— 4878 条按小时聚合后，4518 条压在单一小时，
   直接指认出 15:10 的 cron 作业；不做分布切片就只能看到"整天都在报错"的模糊结论。
   **聚合异常先按时间分桶，多半直接命中触发源。**
