# 2026-09-02 verification-guard-quietly-dead-two-ways

✅已升级(2026-09-06) — 校验关卡自身失效却持续报"正常"，护栏形同虚设（连续 3 轮挂着未修）。

## 现象
`automation-1781663740184`（📊【系统维护】Quant 数据管线）的 PHASE 3 校验步骤
从未真正生效，但每轮的记录都写着"验证通过"。原因有两个，各自独立致命。

## 根因 A：类型不匹配 → SQL 硬报错，退出码被吞
- `daily_kline.trade_date` 是 **TEXT** 类型。
- 校验 SQL 写的是 `WHERE trade_date >= CURRENT_DATE - INTERVAL '90 days'`。
- Postgres 实际报：`ERROR: operator does not exist: text >= timestamp without time zone`。
- 查询失败 → 取不到数字 → 但外部用 `| tail` / `head` 管道消费输出，
  **退出码变成管道最后一条命令的退出码**，报错被吞掉。

## 根因 B：统计口径未按目标集过滤 → 被无关数据垫过阈值
- 原判据是全表 `COUNT(DISTINCT ts_code) >= 20 且 MAX(trade_date) = 今天`。
- 表里另有 37 只**后缀式遗留标的**（`000001.SZ` 格式，冻结于 2026-06-26，永不更新）。
- 这 37 只把"股票数"稳定垫到 70，**即使本管线一只都没写入也能达标**；
  且只要有任何 1 只写入，`MAX(trade_date)=今天` 即成立 → 部分写入完全检不出。

## 修复
1. 日期比较一律加 `::date` 强转。
2. 主判据改为「池内今日写入数 TODAY_N vs 股票池只数 POOL_N」**硬比对**，
   差 1 只即告警；统计一律加格式过滤 `ts_code ~ '^[A-Z]{2}[0-9]{6}$'`。
3. 补充数据质量扫描（close≤0 / high<low / vol≤0 / close 空值）。
4. 已知豁免标的显式列出（如 SZ002354 停更 2026-07-10），避免噪声但保留可见性。

## 通用规则（可迁移到任何带"自检/巡检"步骤的自动化）
- **校验步骤必须验证它自己能跑通**。写自动化时先单独实跑一次校验 SQL，
  确认返回的是数字而不是 ERROR。没实锤跑通过的校验 = 没有校验。
- **凡用 `| tail` / `| head` / `$(...)` 消费命令输出，退出码会被管道吞掉**。
  要判成败就用 `${PIPESTATUS[0]}`，或干脆不接管道。
- **任何"数量 ≥ 阈值"型判据，都要先问：这个数量里有多少是不该被算进来的？**
  历史遗留 / 其它来源 / 其它格式的数据会把阈值垫穿。判据必须限定到目标集，
  最好是"实际完成数 vs 应有数"的等式，而不是"总数 ≥ 某个常数"。
- **滚动窗口的计数环比下降是正常现象，不是数据丢失**。
  本例近 90 天窗口每天滑出约 70 行、滑入 32 行，净 -39 行纯属窗口效应。
  判定必须锚在"今日写入数"这类绝对量上。已在自动化 prompt 中写明禁止据此告警。
