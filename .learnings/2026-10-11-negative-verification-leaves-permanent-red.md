# ✅已升级(2026-10-11)→R50 —— 做「负向验证」会在 CI 健康检查里**永久留一条假红** —— 删分支不够

**日期**：2026-10-11（PA-012 锁门禁负向验证的**收尾**环节）
**等级**：P2（不误伤数据；但会让巡检长期挂一条**无人能处置**的红灯）
**类型**：false-positive（验证产物的生命周期没被当成问题看）
**状态**：验证分支已删；健康检查侧已加豁免（Claw `qts_pmf_health_guard.scan_ci`）

---

## 1. 现象

为了验证「锁文件门禁能不能真的拦住一次红灯」，在 **QTS 仓**建了一条一次性分支
`test/lock-gate-negative-20261011`，故意制造失败、确认门禁生效，验完删掉分支 —— 看起来收尾干净。

**但**：跨仓的「QTS/pmf CI 健康检查」从此长期报 `1 项异常`。追下去，红灯正是这条**已删除分支**
上那次**故意的失败**：

```
{"workflow": "Security Scan", "conclusion": "failure",
 "branch": "test/lock-gate-negative-20261011"}      ← 分支早没了，run 记录还在
```

## 2. 根因

**GitHub 的 workflow run 记录不随分支删除而消失。** 而健康检查原判据只覆盖三态
（默认分支红灯 / PR 分支红灯 / PR 已 MERGED·CLOSED 豁免），**漏了"分支已不存在"这一态** ——
一次性验证分支没有 PR，于是被当成"未合并 PR 的红灯"计入。

## 3. 对**做验证的人**的规则（本条重点）

> **做负向验证（故意制造失败以验证门禁）之前，先想好它会在哪里留下痕迹、谁来清。**

- 会留痕迹的地方至少有两处：**仓里的分支/标签** + **平台侧的 run 记录**（后者删不掉）。
- 因此负向验证的**收尾不只是删分支**，还要：
  1. 确认该痕迹**不会让跨仓健康检查/告警长期误报**（查一遍相关巡检项）；
  2. 若判据没覆盖"分支已删"这一态 → **去修判据**（这才是根治），别只清分支。
- 同族：负向验证若留下了**数据副作用**（写坏的记录、被改的状态文件），同样要显式复位。

## 4. 修法（健康检查侧，已做）

非默认分支 + 无 PR + **分支已从远端删除** → 判为孤儿红灯，不报；
`_branch_exists` 查不到时**维持原判**（判不了不许当没问题）。并补了反向对照测试：
分支还在、只是没开 PR → **仍须报**。
