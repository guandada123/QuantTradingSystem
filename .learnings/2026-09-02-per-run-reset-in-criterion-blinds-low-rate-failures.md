# 判据里只要存在「每轮重置」的项，低频持续故障 100% 测不出来

- 日期：2026-09-02（统一巡检中枢 run#63）
- 级别：P1（哨兵失效，且是 run#54 同型的第三次复发）
- 状态：已修复并部署（Claw `bdbf7c8`，已 push）
- 影响面：Check #16「QTS API 鉴权」；同型风险面覆盖所有「增量锚点 / 滚动窗口 / 计数阈值」类检查

## 现象

`check_qts_api_auth()` 的 401 增量锚点在 run#63 被推进了（`last_seen_ts` 从
`09-01 12:38Z` → `09-01 18:34Z`），但检查自身报 **✅ 0 项异常**。

即：**有新增鉴权失败，哨兵一点反应都没有。**

## 根因

旧实现每轮结束**无条件**把锚点推到本轮最新一条 401 的时间戳，无论本轮有没有告警：

```python
if max_ts > 0:
    _save_qts_auth_anchor(max_ts)   # ← 不看有没有告警，一律推进
```

于是「每轮新增 < 阈值(10)」的**持续**滴漏被逐轮吸收、永不累积：

| 每轮新增 | 折合每天 | 哨兵告警次数 |
|---|---|---|
| 1 条 | 24 条 | **0** |
| 5 条 | 120 条 | **0** |
| 9 条 | 216 条 | **0** |

对照：run#53 定位的系统性漏配是每轮固定 **14 条**（批量）→ 能命中阈值 10。
所以这个哨兵**只抓得住「一次性大批量」，抓不住「细水长流」** —— 而后者才是
生产里真实故障更常见的形态。

## 为什么这是 run#54 的同型复发

| | run#54 | run#63 |
|---|---|---|
| 失效机制 | 24h 滚动窗口 + 去重键数字归一 | 增量锚点每轮重置 + 阈值 10 |
| 共同点 | **判据里有一项会被周期性重置** | 同 |
| 后果 | 告警一次后失明 24h | 低频故障永远不告警 |

抽象出来：**任何「每轮都归零/推进」的状态项，都会把"低频但持续"的信号
挡在阈值之下。** 增量锚点本身没错（它修掉了存量误报），错在它顺手把
计数也一起重置了。

## 修复

锚点状态从单个 `last_seen_ts` 扩为 `{last_seen_ts, pending, pending_since}`：

- `pending` **跨轮累加**，不再随锚点推进而清零
- 只在两种情况下归零：①**告警已发出**（避免同一批事件被重复计入）②**静默 > 24h**
  （避免一次人工调试残留的 7 条，两周后被偶发 3 条凑够 10 条误报）
- 告警文案改为「累计新增 N 次（自 X 起，跨轮累计；本轮新增 M 次）」
- 未达阈值时 note 输出「累计 N/10 条」，让累计进度可见

## 验证（关键：反向验证做对了一次、做错了一次）

**第一次做错了**：我用「把 `QTS_AUTH_PENDING_STALE_SECONDS` 改成 -1」来模拟旧逻辑，
但合成时间戳取在了**未来**（T0 = 2026-09-02 03:00Z，而当时 now = 09-01 19:5x UTC），
`now - ref_ts` 为负，stale 分支根本没触发 —— 等于新逻辑跑了两遍，两遍都告警。
**如果我信了这个结果，就会得出"旧逻辑也会告警、修复无意义"的错误结论。**

**重做（进程隔离 + 时间戳取在过去 4h）**：

```
=== 新逻辑（跨轮累计）===
  round1(累计 5 条): 静默 note=累计 5/10 条
  round2(累计 10 条): ALERT(累计新增 10 次…)
  → 首次告警轮次: 2

=== 旧逻辑（每轮无条件重置累计）===
  round1(累计 5 条): 静默
  round2(累计 10 条): 静默
  round3(累计 15 条): 静默
  → 首次告警轮次: None  (永远不告警)
```

回归两项：单轮 14 条仍一次性命中；零新增仍静默（存量不误报）。

## ✅已升级(2026-09-06)（8 条）

1. **★ 判据里出现「每轮重置 / 每轮推进」的状态项，必须立刻推演低频持续故障会不会被测不出来**
   —— 这是本轮唯一需要记住的判据。run#54（滚动窗口）、run#63（增量锚点）都是它。
2. **★ 修"误报"的改动要同步检查它有没有引入"漏报"** —— 增量锚点是为修存量误报加的，
   它确实修好了误报，却顺手把计数一起重置了。单向优化告警判据 = 半边修复。
3. **★「阈值」与「累计窗口」是两个独立维度，必须分开设计** ——
   阈值决定"多大声算异常"，累计窗口决定"多久内的声音加总"。只设阈值不设窗口 = 只能测突发。
4. **★ 反向验证必须确认变量真的被改变了** —— 我改常量模拟旧逻辑，但时间戳在未来使分支没触发，
   跑出来"修复无效果"的假结论。**反向验证跑完要先自检：我期望看到的差异出现了吗？没出现就是没验证。**
5. **★ 反向验证里的时间戳必须落在"真实可达"的区间** —— 用未来时间戳做条件分支测试，
   `now - X` 恒为负，所有"超时/过期/stale"类分支一律走不到，测试通过是假象。
6. **★ 输出字段必须有出口，否则等于没算** —— `note` 进了 17 个检查的返回字典，
   从没有任何消费者。加字段时先问：谁会读它？
7. **★"只记录不推送"的信息要单独确认它有出口** —— 日志是唯一出口时，
   就必须确认那行日志真的会被打到自动化运行记录里，而不是只进 stdout 被吞掉。
8. **★ 同一个值/同一个语义在多处重复实现是缺陷温床**（本轮第 4 次出现）：
   阈值 10 的语义散落在「判据」与「状态推进」两处，改一处没改另一处即产生死区。
