# 定时任务 24×7 空跑：交易时段守卫缺失 × cron 缺 day_of_week

- **日期**: 2026-09-01
- **等级**: P1
- **发现途径**: 统一巡检中枢 run#59 人工深挖（脚本 16 项全绿，人工发现 2 个 P1 + 1 个监控盲区）
- **状态**: 已修复并部署（QTS commit `84b8d7d2`；中枢新检查项 Claw `44f8fb1`）
- **✅已升级(2026-09-06)**: 8 条

---

## 现象

巡检中枢 16 项 **15✅/1⚠️**（仅微信公众号登录过期），脚本判定 SILENT。
人工深挖容器日志后发现两处独立的持续性浪费：

| # | 问题 | 量化 |
|---|------|------|
| A | `market_snapshot` 30min 无条件间隔，**24/7 不间断** | 每天 48 次里约 **40 次落在非交易时段**；每次耗时 **19.5s**；`index_snapshots` 全天 24h 每小时 16 行，**91% 为无效重复快照** |
| B | 日行情刷新/收盘归总/AI复盘三个 cron **缺 `day_of_week`** | 08-29(六) 耗时 **759.5s**、08-30(日) **720.8s**，各遍历约 4494 只标的；周末零行情，**100% 无效调用** |

**关键**：这两个问题**不报错、不告警、健康检查全绿**。A 的作业每次都
`executed successfully`，B 的作业也 exited 0 —— 从任何"成功/失败"视角看都正常。

## 识别方法（可复用）

### 1. 按小时分桶，一眼看出"无差别执行"
```bash
docker logs -t quant-strategy --since 24h | grep "大盘快照完成" | cut -c1-13 | uniq -c
```
若某个"业务语义上只该在特定时段跑"的作业，在 00:00–23:00 各小时**均匀分布**，
它就一定是无差别执行。这是零成本的第一道筛子。

### 2. 用下游数据反查"产出是否有信息量"
```sql
SELECT to_char(recorded_at,'HH24') hr, count(*) FROM index_snapshots GROUP BY 1 ORDER BY 1;
```
A 股交易时段只有 4 小时（9:30–11:30 / 13:00–15:00），若一张"盘中快照表"
24 个小时桶都有数据，多出来的就是**静态重复值**。
**表的行数分布本身就在告诉你采集频率合不合理。**

### 3. 周末/节假日的作业日志是最干净的对照窗口
`docker logs --since/--until` 圈定周末，看有无"本不该跑"的作业执行。
周末无行情 ⇒ 任何行情类作业的执行都是纯浪费，**不需要任何阈值判断**。

## 根因

**不是某个 bug，而是两个"没人问过"的设计缺失：**

1. **间隔型作业（interval）天然没有"该不该跑"的概念。**
   `add_interval_job` 只表达"多久一次"，不表达"什么条件下值得跑"。
   注册时看似合理，但业务语义（盘中才有行情）从未被编码进系统。

2. **`day_of_week` 是逐个作业手写的，漏写不会报错。**
   代码库里 9:00 的智能选股扫描**有** `day_of_week="mon-fri"`，
   而 15:10/15:20/15:30 三个作业**没有** —— 同一个文件里两种写法并存了数月，
   说明这不是"不知道要加"，而是**没有机制保证一致性**。

3. **放大器：容器 TZ=UTC 而 APScheduler trigger 硬编码 `Asia/Shanghai`。**
   两者不一致。若想当然地在作业里写 `datetime.now().hour` 判断交易时段，
   会**整体偏移 8 小时** —— 这正是本次新增工具时必须用 aware datetime 的原因。

## 修复

1. **新增 `shared/trading_calendar.py`** —— 交易时段判定的单一真源：
   - 一律 `datetime.now(timezone.utc)` 取 aware 时间再显式转北京时间，
     **不依赖进程本地 TZ**。将来容器加 `TZ=Asia/Shanghai` 后行为不变。
   - naive 输入按 **UTC** 解释（当前容器约定），并在 docstring 写明。
   - **不内置节假日表**：A股节假日每年另发，猜错会导致交易日漏跑 → 当日数据缺失。
     「多跑几次无效任务」代价远小于「漏跑一次」，故支持 `extra_holidays` 按需注入。
2. `market_snapshot()` 开头加守卫，**且放在任何数据源调用之前**
   （放在后面就省不下那 20s 与 Tushare 配额）。
3. 三个 cron 补 `day_of_week="mon-fri"`。

**生产实测**：非交易时段 `19500ms → 3.4ms`，日志明确打出 `skipped=True`。

## ✅已升级(2026-09-06)（8 条）

1. **「多久跑一次」不等于「该不该跑」。** interval 型调度只表达频率、不表达前置条件；
   凡语义上依赖外部状态的作业（行情/交易/营业时间），必须在函数入口加守卫，
   而不是指望调度器替你判断。
2. **无差别执行最快的暴露方式是按小时分桶。** 业务上有明显时段特征、
   但日志在各小时均匀分布 ⇒ 一定是无差别执行。零成本，第一个就该做。
3 **下游数据的分布会反诉上游采集是否合理。** 一张"盘中快照表"若有 24 个小时桶，
   其中 20 个必然是静态重复值 —— 不需要懂业务也能看出问题。
4. **同一个文件里同一属性两种写法（有/无 `day_of_week`）＝ 一致性靠人肉。**
   凡是"漏写不报错"的可选参数，都要么抽成公共封装，要么加 lint/测试兜底。
5. **判交易时段绝不能用 `datetime.now().hour`** —— 进程 TZ 与调度器 TZ 可能不同。
   一律 aware datetime + 显式目标时区，并在工具里固化这个约定。
6. **不确定的外部规则（节假日表）宁可不内置。** 猜错的代价（漏跑→数据缺失）
   远大于保守的代价（多跑几次→浪费）。把不确定项做成注入参数。
7. **守卫必须放在任何 I/O 之前。** 加守卫却放在取数之后，
   省下的只是"写库"，耗时与配额照付 —— 收益归零。
8. **加守卫会让既有测试变成时序依赖**（见下坑②）。改调度类行为时，
   必须全局 grep 相关测试并显式固定时间，否则 CI 结果随运行时钟漂移。

## 坑（实犯）

### ① `docker logs | cut -c1-13` 分桶时，UTC 小时 ≠ 北京时间
容器日志时间戳是 UTC（`Z` 后缀）。本次"4518 条压在 07 时"= **北京 15:00–16:00**。
分桶后必须换算再对照 cron 配置，否则会对不上作业时间、误判成"没有对应作业"。

### ② 加守卫后 3 个既有用例静默失效（本次实犯）
`test_market_snapshot_success` 等在**未固定 `is_trading_time`** 的前提下断言
`mock_db.execute.call_count > 0`。守卫一加，夜里跑 CI 全部静默跳过 → 断言失败。
更隐蔽的是：白天跑会全部通过，**CI 结果随时钟漂移**。
修法：所有相关用例显式 `patch("shared.trading_calendar.is_trading_time", return_value=True)`，
并**补一个 `return_value=False` 的跳过用例**（断言连 `DataService` 都没被构造）。

### ③ `grep "401\|403"` 会命中纳秒时间戳里的数字
`2026-09-01T11:29:38.403010713Z` 含 "403"，`...827401344Z` 含 "401"。
诊断 401 必须用完整模式 `'HTTP/1.1"'` + 解析状态码字段，不能裸 grep 数字。

### ④ 手写时间戳解析容易多拼一个小数点（本次实犯）
```python
frac = frac[:7]          # ".669403"  含点！
dt = fromisoformat(head + "." + frac)   # → "....669403" 双点 → 解析失败 → 返回 0.0
```
而**下游的"解析失败保守计入新增"兜底会把这个 bug 放大成满屏误报**（run#54 同一条坑）。
确认过 232 条全是 0.0 才发现是自己的解析错了，不是真有 232 条故障。

### ⑤ `task_scheduler.list_jobs()` 返回 dict 不是 Job 对象
`j.name` 会报 `'dict' object has no attribute 'name'`，要用 `j.get('name')`。

## 复用写法

1. **「跑了」不等于「该跑」，更不等于「干成了」。** 三层递进：
   执行 → 有效 → 有价值。本次 A 三层全过（执行成功、有数据、有值），
   但 91% 的价值为零。校验数据管道要问"这批数据有没有新增信息量"。
2. **周末/节假日是最干净的对照窗口**：业务量恒为零，
   任何执行都是纯浪费，判定无需阈值。
3. **"部分成功掩盖完全失败"第 4 次复现**（QTS backtest_reports / pmf 3 作业 /
   Tushare 100% 失败 / 本次 91% 无效快照）→ 已成模式，见独立 learning。
4. **改调度行为要连带改测试的时间依赖**，否则得到的是一个
   "白天绿、夜里红"的 CI —— 比一直红更难发现。
